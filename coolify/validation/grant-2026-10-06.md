# Normal Appbox validation: Coolify r8

The Ubuntu 26.04 image was installed through the normal Appbox flow on the
designated test Appbox, with four CPUs, 8 GiB RAM and an 18,000 GiB virtual
disk. The sealed image came from package commit `eb8908d`; no initialized
customer disk was published. The app and version remain admin-only.

Cold installation reached its authenticated callback. Owner login, masked
password Show/Hide, pinned SSH, Docker and bundled-service health passed.
The fixed root filesystem and separate XFS data filesystem mounted correctly.

A disposable nginx Compose project deployed through Coolify and served its
exact test content over public HTTPS through the existing nginx stream route.
Realtime and terminal WebSockets completed HTTP 101 handshakes and exchanged
frames. The web terminal wrote and read markers in a Docker named volume on
the data filesystem.

A normal Appbox restart reached a new boot. Eleven generated identities,
account and project settings, a fsynced data fixture and both project-volume
markers survived. Dashboard and project HTTPS returned 200 again. The package
password-recovery helper accepted a temporary password and rejected the
previous password, then restored and verified the original. Fresh owner login
and terminal marker readback passed afterward.

The supplied wildcard certificate matched the protected proxy copy and
private key. It covered dashboard and project hostnames and was valid. The
sync timer was active, and repeated sync succeeded without a configuration
change. Future renewal, TLS-ALPN issuance without supplied certificates, and
an application upgrade remain unverified. Shared user storage is outside
this package; its own-volume tests do not qualify that workflow.

Full-size trimming failed. During the OS fstrim operation, dashboard requests
returned gateway timeouts and guest tasks waited on disk I/O. Guest full I/O
pressure reached 91.46% over ten seconds. Host evidence also showed a QEMU
worker waiting on the backing XFS filesystem. This locates the stall in the
disk path without establishing a kernel, QEMU or disk defect.

Reducing the guest discard request limit from about 2 GiB to 64 MiB did not
resolve sustained I/O pressure. The original setting was restored. A normal
service stop ended with a timeout and exit status 15. After it exited, blocked
tasks cleared, the dashboard recovered and full I/O pressure fell to 1.58%.
Trimming was inactive after reboot. The successful 64 GiB clone preflight
therefore does not qualify trimming on the full-size Appbox disk.

A separate reboot check found the existing installation callback retrying
with HTTP 401 after its one-time token had been consumed. Cold installation
had completed correctly. Shared callback, lifecycle and host settings were
not changed. The package needs a verified way to avoid replaying a completed
installation callback on later boots.

The image remains a private preview. Full-size trim and the reboot callback
retry need resolution and fresh qualification before readiness can be
claimed. Detailed infrastructure receipts and authenticated screenshots are
retained locally under the Git-ignored validation/private directory.
