# Normal Appbox validation: Coolify r9

The r9 image (package commit `9a167fb`, sha256 `7ec41dec…3d52`) was copied
to the test host with a verified checksum. It was registered as admin-only
version 1504 with the same resources as r8: four CPUs, 8 GiB memory, swap
and reservation, and eight app slots. Instance 265544 was installed through
the normal Appbox flow on the designated test Appbox with an 18,000 GiB
virtual disk.

Cold installation reached its authenticated callback, and central state
moved to installed. The package recorded the callback as complete. Owner
login in Chrome and masked password Show/Hide passed. Public SSH matched the
host keys printed on the VM console. `/data` is XFS, mounted with `discard`,
and its fstab entry and both bind mounts carry `X-fstrim.notrim`.

Trimming no longer stalls the VM. The hourly timer ran on the full-size disk
about five minutes after setup finished. It took three seconds and trimmed
`/` and `/boot` only. A manual run took 0.14 seconds. Deleting a 2 GiB file
on `/data` released all 4,194,304 sectors to the host in 0.7 seconds, while
dashboard requests stayed at or below 0.41 seconds. One dashboard request
took 11.8 seconds while 2 GiB of random data was being written and fsynced
to `/data`, before the trim started. That was write load, not trimming.

A normal Appbox restart reached a new boot. The installation callback was
skipped by its completion condition, with no retries. Central state stayed
installed. A data-disk fixture, a Docker named-volume marker, the SSH host
key and the machine ID survived. Dashboard HTTPS returned 200 and all
Coolify containers were healthy again.

After the restart, a project hostname was added in Appbox and an nginx
image was deployed through the Coolify UI. It served the nginx welcome page
over public HTTPS with the wildcard certificate. The dashboard realtime
WebSocket connected and joined its private team channel. The web terminal
wrote a marker to `/data` that read back over SSH.

Certificate renewal was tested in two parts. On the VM's writable
configuration share, which uses the same virtiofs supervisor as the
certificate mount, an in-place rewrite and a rename-and-replace on the host
were both visible in the guest within two seconds. Inside the guest, a
replacement certificate and key were mounted over the Appbox wildcard
directory. Within two minutes the guest timer loaded them and Traefik served
the new certificate on the dashboard and project hostnames. Removing the
replacement restored the Let's Encrypt wildcard the same way. The real
host-side renewal of the wildcard, due in December, was not exercised.
Superseded certificate and key copies stay under
`/data/coolify/proxy/certs` after a renewal; the test copy was removed by hand.

A custom hostname, `test1.appbox.pro`, was added to the VM in Appbox. The
host already held a certificate for it from an earlier test. In that case
the host's certificate job returns before attaching the certificate to the
VM, so no certificate mount appeared and the VM was not restarted. This is
platform behaviour outside the package. Attaching a newly issued
custom-domain certificate is therefore still unverified.

That left the hostname routed to the VM without a supplied certificate,
which is the case TLS-ALPN covers. After the hostname was added to the
nginx project in Coolify and the project redeployed, Traefik obtained its
own Let's Encrypt certificate through the TLS challenge on port 443 within
about two minutes. HTTPS returned 200, and plain HTTP redirected to HTTPS
with a 301. In-place upgrade does not
apply because the app sets `can_update: false`. Shared user storage is
outside this package. The app and version stay admin-only. Detailed
receipts are kept locally under the Git-ignored `validation/private`
directory.
